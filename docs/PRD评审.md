# 《课集》PRD v0.3 评审意见

评审日期：2026-10-13。初次评审对象为 [PRD.md](PRD.md) v0.3；对照材料为[水晶排课官网操作说明](https://www.myzan.cn/help/index.html)、本地[逆向需求文档](crystal-scheduling-analysis/需求文档.md)和[深层代码分析](crystal-scheduling-analysis/evidence/深层代码分析.md)。本评审检查需求的内在一致性、可实施性、可验收性及来源边界；没有运行新产品或对性能做基准测试。PRD 后续已按用户要求修订为 v0.4。

> 修复追踪（2026-10-13）：用户要求保留 F06 的 P0 范围，其余意见已写入 [PRD v0.4](PRD.md)。F01→US-003/012/013；F02→US-005/010/014/020；F03→US-004/006/032、V15；F04→US-017/019/021、V7/V8；F05→G3、8.2、V17/V18；F07→US-027/029/031、教学日历；F08→US-019/023、状态机；F09→US-038/039、8.3；F10→US-041、V16；F11→背景/状态/来源；F12→US-041、9.2。以下是对 v0.3 的原始评审记录，所引行号指修改前版本，仅保留问题说明，不作为 v0.4 当前行号。

## 需在需求基线前解决

### F01｜单双周容量校验会漏掉单侧超载（高）

位置：PRD.md:250–259、:665–666。US-013 只要求“两周合计”不超过两周格子数。假设一个班每周只有 1 个可用格，两周共有 2 格；录入 2 节单周课、0 节双周课，总量恰好为 2，却无法在单周放下。必须同时校验单周、双周各自的容量，以及每周课占两侧格子的事实。还需规定“每周/单周/双周节数”的录入值是每次出现周的节数还是两周累计节数，以及一个班同一科目能否同时有“每周 3 节 + 单周 1 节”。

建议：在 US-013 AC3 改成分别计算 `每周课节数 + 单周课节数 ≤ 单周容量`、`每周课节数 + 双周课节数 ≤ 双周容量`；若单、双周作息不同，容量也分别计算。V4 增加上述“总量合格但单侧超载”的反例。定义学期起始周的单双周锚点，供调代、统计、导出使用。

### F02｜跨学段时间修改与冲突检测相互矛盾（高）

位置：PRD.md:178–184、:223–229、:331–338。US-005 AC4 说节次时间修改“不影响排课数据”，US-020 又用该时间判定跨学段教师冲突。已经排好的两节课只要改动其中一学段的时间，就可能立即重叠。跨学段合班也只有“时钟映射对齐”，没有定义起止时间相同、部分重叠、课长不同的处理。

建议：时间改动不自动移动课节，但必须重新检测所有受影响教师、合班和场室，列出新冲突并要求处理；定义跨学段合班只有起止时间完全一致时才可绑定，或明确允许的容差与业务规则。V5 增加“排完课后修改时间”的回归用例。

### F03｜“自习”同时被建模为免任课文字和可值班时段，入口不通（高）

位置：PRD.md:169–176、:186–192、:436–459。US-004 的“自习”格始终不排正课；US-032 又规定仅标记为“自习/值班类”的时段类型才能建立值班需求。教务员若按原软件习惯把某班某格设为免任课“自习”，按当前规格无法为该格安排看班教师。反过来把整段“晚上”标成值班类，可能使正常晚间课程也允许建值班需求。

建议：把“教学时段类型”“单个格子的教学占用状态”“值班需求”拆成独立概念。明确免任课“自习”是否可作为值班位置；若可以，US-032 应按班级具体格子的用途建需求，而非仅凭全局时段类型。V15 加入这一操作路径。

### F04｜求解器的验收标准缺少质量与失败口径（高）

位置：PRD.md:289–347、:667–670。US-017 将五类自定义条件全部定义为硬约束，US-021 又要求无法满足时“相关课程”进暂放区并逐条说明冲突来源。对互斥、固定次数、跨班教师等组合，究竟暂放哪一节、报告“违反的候选条件”还是“导致不可满足的最小原因”，没有定义；后者通常需要额外求解。软性偏好只有“尽量”，没有可比较的评价口径。逆向证据只支持部分候选门控、随机搜索和一个局部双指标比较，尚未恢复完整优先级；官网手册也只描述操作与偏好语义，不能代替新产品的验收规则。[官网开始排课说明](https://www.myzan.cn/help/5.html)。

建议：为每项规则给出适用范围、硬/软分类、违反时的输出、同等可行解的评价次序；报告先承诺可核验的“未安排课程 + 当前阻断条件”，把“证明最小冲突集”作为另行评估的能力。给 V7/V8 固定小规模算例及期望结果。固定随机种子应连同输入数据版本、求解器版本和线程策略一起记录，否则“同种子必相同”无法稳定验收。

### F05｜已确认的性能红线没有可执行的验收设计（高）

位置：PRD.md:49–56、:633–641、:679。G3 写 400 班/800 教师从零录入到排课 ≤2 小时、正常档 ≤5 分钟，8.2 又给拖动 <200ms、打开/保存 <3 秒；V17 只要求 600 班规模“不崩溃，耗时记录并回填”，并未验证这些阈值。没有定义硬件、数据生成器、课程密度、硬约束密度、成功排出率、重复次数和分位数。只追求 5 分钟还可能通过大量暂放课“达标”。

建议：把 400 班等数字标为目标规模，而非已证实基线。定义标准数据集与机器、成功排出率/未排量上限、P50/P95 耗时和测量起止点；V17 分别验证典型规模的时间目标与极限规模的稳定性。零录入 2 小时须说明是否允许 Excel 批量导入及数据是否预先整理。

### F06｜“P0 最小闭环”同时承担大量新模型，发布范围过满（高）

位置：PRD.md:45–56、:124–136、:681–685。P0 同时包含三平台桌面、学段和跨学段时钟、按天不同作息、自定义时段、单双周、完整五类约束与启发式求解、交互调课、Excel 导入导出和打印、自动暂存备份。每一项都会改动课程位置、冲突检测、导入模板与打印模型；组合验证成本高。P1 才含调代与统计，监考明确不做，因此 G1 的“可替代水平”也不能按原软件全功能解释。

建议：定义“可替代”的具体学校类型与场景，按可验证的纵向闭环分阶段：先单学段/每周/基本约束/手工编辑/导出备份，再扩展跨学段和单双周；若业务决定两者必须 P0，则应同步调整工期、团队与 beta 范围，并把组合用例列入里程碑。此项是范围与交付风险，不否定 D11/D6 本身。

## 应补充明确规则

### F07｜学期日历缺失，调代和工作量无法按“实际出现次数”结算（中高）

位置：PRD.md:250–259、:412–434、:593–614。US-029、US-031 按起止日期和单双周实际出现次数统计，但数据实体没有学期开始日期、单双周锚点、停课/调休/节假日、临时任务相互覆盖时的优先级。周模板本身不能确定某个自然日究竟属于单周还是双周；两个有效任务同日改同节课也可能重复计数。[官网工作量页](https://www.myzan.cn/help/23.html)只说明期限和应上/实上/调代节数，并未给出新产品的单双周日历语义。

建议：新增“学期日历/教学日”实体，明确第一周周次、例外日与补课日；定义任务生效区间重叠时的优先级、继承改动的快照/传播规则，列出一组跨单/双周与假日的手算期望值。若暂不支持例外日，统计表须明确按标准周模板估算，不能称为实际发生节数。

### F08｜“锁定”粒度与状态机不一致（中）

位置：PRD.md:321–329、:362–377、:545–559、:609。US-023 只定义锁定班级或教师课表，状态机和实体却把“锁定”当作单节课属性，US-019 又要求自动排课保留已锁课节。两种锁粒度决定不同的数据结构和局部重排语义；同时，原软件 `SavePai` 代码有清理班/师 `islock` 的分支，不能把重排保锁视为已确认的原软件行为。[本地代码分析 C06](crystal-scheduling-analysis/evidence/深层代码分析.md#c06结果保存与未排课程)。

建议：明确是单节、班级、教师三类锁，或仅后两类；定义冲突叠加和解除后的行为。把“自动重排保锁”标为新产品要求，并给 V8/V9 分别加班级锁、教师锁、单节锁（若支持）测试。

### F09｜文件安全目标写成了不足以保证目标的实现手段（中）

位置：PRD.md:495–510、:565、:643–647。8.3 将“临时文件 + 替换”直接等同于“断电不损坏”，但跨平台的磁盘刷新、目录刷新、旧版保留与恢复验证都未定义；自动暂存可能发生在排课取消或导入尚未提交时。US-038 的自动镜像还未说明触发节点、保留清理、备份校验、打开镜像是否修改当前工作数据。原软件有 16 字节头标记和文件复制流程，但这些不能证明新产品的原子性。[本地代码分析 C08](crystal-scheduling-analysis/evidence/深层代码分析.md#c08本地文件加载及固定头标记)。

建议：PRD 保留结果级要求：“任一保存中断后，可打开最近一次完整提交的数据或恢复前副本，未提交修改不外泄”；具体写入策略放到技术方案。规定排课、导入、恢复、自动暂存之间的事务边界，做断电/磁盘满/文件占用故障注入验收。

### F10｜一机一码且不能换机，缺少设备变化和离线恢复口径（中）

位置：PRD.md:75–97、:525–534、:573–589。D15 是明确的商业选择，但“换设备需另购”没有界定系统重装、硬盘更换、主板维修、虚拟机迁移、设备码误变、激活码遗失。离线永久使用与绑定设备并不冲突，前提是本机如何验证签名、失效原因如何解释均可实现和测试。当前 V16 只测“换设备提示另购”。

建议：补设备码稳定性规则、同机重装的恢复方式、损坏设备的售后政策、离线授权文件的校验/撤销边界；这是对已定商业模式的实施细则，不要求更改 D15。

### F11｜来源标记和事实表述有误（中）

位置：PRD.md:13–19、:35–43、:689–704。逆向账本已逐字节核验的是 **67 个窗体、1942 个组件**，PRD 写成 1992。原软件数据可通过官方 Excel 导入/导出部分业务数据、可备份 `.yqd` 并在另一台电脑恢复，故“跨软件、跨电脑迁移只能依赖手工备份文件”过于绝对。[官网总览](https://www.myzan.cn/help/index.html)列有备份/恢复，[官网反导入](https://www.myzan.cn/help/11.html)列有 Excel 输入。当前静态样本和官网资料并不足以绝对证明旧产品不存在任何跨学段/单双周能力；建议改成“在本次分析范围和公开操作说明中未见此能力”。

文档声称“全部待确认问题已决策关闭”，但仍有 US-021 阈值“待验证”、跨学段合班、日历口径、值班/免任课关系等未定义项。建议把“业务决策已记录”和“技术/验收语义已冻结”分开，决策记录补责任人和会议/原始记录链接。已确认的 D1–D19 应保留为产品选择，不应因逆向未见就撤销。

### F12｜授权分期与导出体验需要统一说明（中）

位置：PRD.md:124–136、:473–480、:525–534、:681–685。P0 beta 要可导出和打印，M11/P1 才启用免费版限制；首发 beta 到 P1 商业化之间的已创建数据与用户权益没有说明。“免费版禁用所有导入、导出、打印”但备份可完整复制数据文件，这是合理的数据安全例外，却会使“所有导出”一词失真。还需要说明正式版到期不会发生，因为买断；“离线永久使用”的后续兼容政策另议。

建议：写明 beta 是否默认全功能、何时开始授权、旧数据如何继续打开；把禁止范围表述为“结构化表格导入导出及打印，数据文件备份例外”。V16 覆盖从 beta 升级及同机重装。

## 次要编辑建议

- US-008 AC5 的同名教师最好采用稳定教师 ID + 显示区分名，不强制篡改真实姓名；官网反导入用改名规避同名，是原产品输入限制，并非新系统必须沿用。[官网反导入](https://www.myzan.cn/help/11.html)。
- US-033 把“每人每周值班天数上限”放在软性规则中，需明确可否超限；“空白=自动”需定义自动计算方法。V15 加上下限、上限冲突和缺口案例。
- US-036/V12 应确定 Excel 文件和系统打印是否使用同一个版面渲染结果；不同表格软件的字体与分页可能不同。可把验收表述为内容/结构一致、打印 PDF 或预览与本应用输出一致，避免要求三种软件逐像素一致。
- 7.2 的本机“启动次数/功能使用计数”虽不上传，也属于本机使用记录；建议写明默认启用与否、保存位置、清除方式，并将标题“数据与埋点”改为“数据与本机诊断”。

## 建议的基线结论

这份 PRD 已把大量原产品操作流程转成可读用户故事，追溯方向总体清楚；但 F01–F06 会造成相互冲突或无法判定通过的开发验收。在修正这些条目、补充 F07–F10 的关键边界后，再把文档标为“已冻结需求基线”。本文只评审规格，未对 D1–D19 的真实业务批准过程作事实判断。
